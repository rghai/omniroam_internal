Technical decision in plain English

One manageable system, with replaceable providers and hard safety gates.

The storefront, checkout, provider connections and founder operations begin together, without locking Omniroam to one supplier or payment company.

Recommended production shape

Use one TypeScript application on Vercel and managed PostgreSQL as the system of record. Keep clear internal boundaries for catalog, pricing, checkout, payments, fulfilment, events, notifications and operations. This “modular monolith” is simpler for two founders than multiple services while preserving clean seams for future growth.

The non-negotiable rule

One successful customer payment can create no more than one supplier order.

Every payment, webhook and fulfilment action must be safe to retry without duplicating money or eSIMs. Unknown states are reconciled; they are never blindly repeated.

How an order should move

  1. Create an immutable quote with retail, supplier cost, FX and margin.
  2. Create one pending order and one payment attempt.
  3. Accept payment through tokenised Opn fields; secrets stay server-side.
  4. Verify the result using API state and signed webhook evidence.
  5. Create one deterministic eSIMAccess transaction only after payment is confirmed.
  6. Poll/reconcile until the eSIM profile is ready, then send install instructions.
  7. Record every state change and surface exceptions to operations.

Replaceable provider adapters

Opn / Omise

Test and live modes remain separate. Browser tokenisation uses only the public key. Secret-key API calls and webhook verification happen server-side.

eSIMAccess

Request signing, rate limits, asynchronous allocation, delayed usage and supplier transaction IDs are isolated behind one adapter.

Fake adapters

Deterministic success, delay and failure fixtures let us test the complete journey without supplier spend.

Future providers

Another supplier or payment provider can implement the same internal contract without rewriting the storefront.

Current safe implementation

  • Catalog and brand values live in configuration files.
  • Customer plan selection and demo checkout work.
  • Opn test payment and one bounded supplier order have been proven.
  • Live supplier writes remain off.
  • Database, idempotency store, durable webhook inbox/outbox and reconciliation jobs remain to be implemented.

Acceptance criteria before live automation

  • Managed database provisioned, backed up and restore-tested.
  • Concurrency test proves one charge and one supplier order.
  • Verified webhook receivers plus deduplication and replay controls.
  • Scheduled reconciliation for payment, fulfilment, usage and event delivery.
  • Kill switches for payment and supplier writes.
  • Structured logs, actionable alerts and tested incident runbooks.
  • Secure order recovery and installation pages.
  • Daily payment-to-order-to-supplier financial matching.
