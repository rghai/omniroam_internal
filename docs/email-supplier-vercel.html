Transactional email

Omniroam sends the customer email.

We do not rely on eSIMAccess's customer email. Resend carries an Omniroam template with plan details, a private installation link, setup steps, a data-only explanation and a warning not to delete an installed eSIM.

The template includes HTML and plain text. Provider and database idempotency stop the same order email being sent twice during a retry. A real Gmail delivery test reached the recipient's mail server on 29 August 2026.

The expired domain is no longer a dependency. The founder canary may use Resend's testing sender, which can deliver only to the Resend account email. Customer delivery waits for the next owned domain, DNS authentication and a monitored reply inbox.

New email remains readable when images are blocked. The private recovery address is plain text rather than a tracked link. It uses a URL fragment, which the browser removes before exchanging it for a short secure session.

How supplier-proof is it?

The customer never sees or chooses the supplier.

Checkout asks Omniroam to fulfil the purchased plan. Omniroam's private fulfilment configuration chooses the supplier connection. The customer sees only Omniroam, their plan, price, coverage and order status.

eSIMAccess now sits behind an internal adapter. A future supplier should require a new adapter, product mappings and protected credentials. Payment, email, recovery and customer pages should stay unchanged.

An endpoint-only swap is unlikely. Suppliers use different authentication, price units, order states, QR fields, webhooks, refunds and usage models. The adapter keeps those differences out of the customer experience.

Remaining portability work

  • contract tests for every supplier connection
  • a neutral product-reference database migration
  • capability flags for top-up, phone numbers and cancellation
  • normalised webhooks and reconciliation
  • a second sandbox connection as proof

Support routing

Customer topics now cover device compatibility, device setup, activation, connectivity, order recovery, top-up, billing, refunds and other problems. Supplier portal or API problems stay internal. Refunds start with a person at Tier 3.

Why checkout does not need Turnstile yet

Opn tokenisation, server-side amount verification, idempotency, rate limits and payment fraud controls are better first-line checkout protections. A Turnstile challenge adds another failure point at the highest-value step. Use it first on recovery, support and privacy forms if abuse appears. Add it to checkout only when measured bot activity justifies the conversion cost.
